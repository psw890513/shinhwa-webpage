1단계 · 첫 요청과 뼈대

한 문단짜리 요청에서 시작

하이 웹페이지를 하나 만들건데 발전기, 양수기 등 산업용 기계들을 임대하는 회사의 웹사이트야. 결제 모듈까지는 필요 없고 회사 소개 / 제품 카탈로그 / 연락 정도로 구성하고 싶어

바로 만든 것

  • 빌드 도구 없는 정적 사이트 (HTML, CSS, JS)
  • 회사 소개, 장비 카탈로그, 문의 폼

이어서 붙은 요구

  • 회사명: 신화 건설 → (주)신화건설기계
  • "제품 등록하는 관리자 페이지랑 접수 내역 확인 페이지도 필요"
  • "Firebase로 해줘" → 데이터 저장 방식 결정

포인트: 처음부터 다 정하지 않아도 됩니다. 만들어진 것을 보고 다음 요구가 자연스럽게 나왔습니다.

2단계 · 일하는 규칙

반복되는 요청은 규칙 파일로

내가 한 질문에 답변한 뒤 확인할 수 있는 링크를 항상 알려줘. 스킬에 정의할 거야, 프로젝트 지침에 저장할 거야?
미리보기 아티팩트는 너가 말하는 가장 마지막에 넣도록 해. 그래야 내가 바로 확인하지
스킬에 항상 한국어 답변 추가

CLAUDE.md (프로젝트 지침)에 저장한 것

  • 답변 뒤에는 확인 링크를 항상, 이전/최신 버전 표시
  • 미리보기 링크는 답변의 마지막 줄
  • 모든 답변은 한국어
  • 사용량이 늘면 무거운 스킬을 빼자고 먼저 제안
  • 작업 순서: 점검 → 계획 → 테스트 → 구현 → 검증 → 합치기

이 파일은 새 대화를 열어도 매번 다시 읽힙니다.

4단계 · 배포

"왜 깃허브에 아무것도 없지?"에서 배포까지

왜 깃허브 소스에 아무것도 없지?
작업은 별도 브랜치에 있고, 기본 화면인 main에는 README만 있었습니다.
main에 합쳐줘
무료 호스팅으로 배포해줘. 도메인 나중에 할거야
  • 저장소가 비공개라 GitHub Pages를 쓸 수 없음 → 사용자가 공개로 전환하기로 선택
  • 설정은 저장소 주인만 가능 → 클릭 순서를 안내, 사용자가 직접 설정
  • 이후 main에 합칠 때마다 1~2분 뒤 자동 배포

5단계 · 작업 체계

스킬로 작업 방식 자체를 정리

dev-check

사용자가 제안한 네 칸 틀(Known/Unknown)을 점검 스킬로 직접 만듦. 정해야 할 것과 현장에 물어볼 것을 구분

superpowers

계획, 테스트 먼저, 디버깅, 완료 전 검증 같은 개발 습관 묶음. 사용량이 늘 수 있어 "많아지면 빼자고 알려줘" 규칙 추가

im-not-ai

한글 문구의 AI 티 점검. 사이트 문구를 검사해 회사소개 한 문장만 다듬음

자동 점검 테스트 (npm test)

PC·모바일 화면, 메뉴 이동, 검색, 견적 폼, 관리자 화면, 로그인과 저장 흐름까지 24개. 바꿀 때마다 실행

기능 점검표

"기능 리스트와 작동 여부, 주의할 점을 아티팩트로 관리해줘" → 기능마다 상태와 주의점을 적고, 바뀔 때마다 갱신

6단계 · 구조 고치기

사용자가 직접 써 보고 찾은 문제

사이트 점검 좀 하자. 왜 메뉴를 클릭하는데 아래로 스크롤이 되는 거지?

원인

모든 내용이 한 페이지에 있고, 메뉴는 그 안의 위치로 스크롤하는 방식이었습니다. 회사소개는 메뉴 맨 앞인데 내용은 맨 아래에 있었습니다.

결정과 결과

"메뉴별 페이지 분리"를 선택 → 임대/렌탈, 회사소개, 견적문의, 공지사항, 오시는 길 5개 페이지. 장비 카드의 견적 요청은 장비를 미리 채운 채 이동합니다.

7단계 · 관리자 기능

방식을 세 번 바꿔 사용자에게 맞췄습니다

  1. ①

    견적 요청 관리

    "견적 요청을 받아서 처리 가능한 관리자 페이지" → 신규 → 연락함 → 견적 발송 → 계약 → 완료, 처리 메모와 기록, 24시간 지연 경고

  2. ②

    Firebase 없이 콘텐츠 관리

    "일단은 Firebase 로그인 없이 콘텐츠 관리하는 것만 하자" → 장비, 공지, 회사 정보, 배너를 GitHub 토큰으로 저장

  3. ③

    Firebase 연결

    토큰 뭔지 모르겠다. Firebase 연동하자

    → 이메일과 비밀번호 로그인, 콘텐츠와 견적 요청을 Firebase에 저장. 설정값은 사용자가 콘솔에서 복사해 전달

포인트: 기술적으로 맞는 방식보다 쓰는 사람이 이해할 수 있는 방식이 남았습니다.

지금의 구조

서버 없이 무료로 돌아갑니다

손님휴대폰·PC
→
GitHub Pages사이트 5개 페이지 + 관리자 2개main에 합치면 자동 배포
↔
Firebase콘텐츠(site/content)견적 요청(inquiries)관리자 로그인

사용자가 관리자 페이지에서 하는 일

  • 장비, 공지, 회사 정보, 배너 수정 → 바로 반영
  • 견적 요청 확인과 처리 기록

지켜 둔 안전장치

  • Firebase를 못 읽으면 기본 콘텐츠 파일로 표시
  • 견적 저장에 실패하면 메일 작성으로 넘김
  • 관리자는 손님이 쓴 요청 내용을 고칠 수 없음
